# Ledgerline - a production-grade SaaS marketplace

A flagship full-stack portfolio project: a multi-tenant marketplace platform for
digital products with **three role-based dashboards**, a **provider-agnostic
payment layer**, a **real analytics engine**, and a **first-class API platform** -
all in one strongly-typed Next.js codebase you can read end to end.

> This is a demo. No real payments are processed; all data is generated by the seeder.

**Repository name:** `ledgerline` (matches the product). If you prefer something
that reads as a portfolio piece, `ledgerline-marketplace` or
`saas-marketplace-platform` also work - the package is named `ledgerline`.

## Highlights

| Area | What's actually built |
|---|---|

| **Admin console** (`/admin`) | Analytics engine (MRR/ARR, ARPU, gross & net revenue churn, NRR) with Recharts · a "database studio" - server-driven tables with multi-column sort, faceted filters and URL-addressable state for Users / Orders / Products / Logs · system health (latency percentiles, webhook delivery, resource metrics) · immutable audit trail |
| **Customer dashboard** (`/dashboard`) | Billing hub (subscribe / change plan / cancel, invoice history, printable invoices) · API-key management (scoped, rate-limited, hashed, usage charts) · security center (profile, password, 2FA with QR, sessions, notification preferences) · order history with self-serve refunds · downloads library |
| **Seller portal** (`/seller`) | Multi-step **digital product builder** wizard (basics → media → pricing tiers → SEO → review) · order fulfillment · refund approval/rejection with provider payout |
| **Storefront** (`/`) | High-converting landing page with an **interactive ROI calculator**, dynamic pricing table (monthly/yearly), feature matrix · catalog with **fuzzy search** (Fuse.js), faceted filtering and sorting · product pages with SEO metadata & verified-purchase reviews · cart → checkout flow |
| **Payments** | One `PaymentProviderAdapter` interface, four implementations - **Stripe, PayPal, PayU** (real REST + signed-webhook verification) and a fully-working **Mock** gateway · idempotent webhook processing keyed on `(provider, eventId)` |
| **API** | `GET /api/v1/products` - bearer-key auth, scope checks, per-key fixed-window rate limiting, request logging, `X-RateLimit-*` headers |

## Tech stack

- **Next.js 16** (App Router, Server Components, Server Actions, Turbopack) - a
  strict superset of everything a "Next 15" brief asks for. Route protection uses
  the Next 16 `proxy.ts` convention (formerly `middleware.ts`).
- **TypeScript**, strict mode, zero `any` in application code
- **Tailwind CSS v4** + hand-authored **shadcn/ui** components + Lucide + Motion
- **PostgreSQL** + **Prisma 7** (driver adapters via `@prisma/adapter-pg`)
- **Auth.js v5** (NextAuth) with the Prisma adapter
- **TanStack Query** + **Zustand** (cart, UI) for client state
- **React Hook Form** + **Zod v4** everywhere a form exists
- **Recharts** for the analytics & health visualizations
- **Faker** seeder - ~200 users, 140 products, 460 orders, 580 invoices, 650 reviews, plus logs/metrics/keys

### Why these choices

- **Prisma over Drizzle** - pairs naturally with the "database studio" feature and
  `prisma studio`; Prisma 7's driver-adapter architecture is demonstrated properly.
- **Auth.js over Clerk** - shows real RBAC / middleware / session-callback
  engineering, runs fully offline, no vendor lock-in.
- **Postgres via Docker** - one command to a reproducible database.

## Getting started

```bash
# 1. Database
docker compose up -d            # Postgres 17 on :5432 (+ Adminer on :8081)

# 2. Environment
cp .env.example .env
npx auth secret                 # writes AUTH_SECRET into .env

# 3. Schema + client + seed data
npm install
npm run setup                   # prisma generate && prisma migrate deploy && prisma db seed

# 4. Run
npm run dev                     # http://localhost:3000
```

The database schema is version-controlled as a Prisma migration in
[`prisma/migrations/`](prisma/migrations) - `npm run db:deploy` (or `npm run
setup`) applies it to a fresh database, no `db push` needed. `prisma/seed.ts`
then fills it with ~200 users / 140 products / 460 orders and supporting data.

## Architecture

```
src/
├── proxy.ts                 # edge route protection + RBAC (Next 16 convention)
├── auth.ts / auth.config.ts # Auth.js v5 - split for edge-safety
├── app/
│   ├── (marketing)/         # public storefront, pricing, catalog, product, cart
│   ├── (auth)/              # sign-in / sign-up
│   ├── admin/               # ADMIN - analytics, DB studio, health, logs
│   ├── dashboard/           # CUSTOMER - billing, API keys, security, orders
│   ├── seller/              # SELLER - product builder, fulfillment, refunds
│   ├── checkout/mock/       # stand-in for a hosted provider checkout
│   └── api/
│       ├── auth/[...nextauth]/
│       ├── v1/products/     # public, API-key authenticated
│       ├── webhooks/[provider]/
│       └── health/
├── components/
│   ├── ui/                  # shadcn primitives (hand-authored)
│   ├── data-table/          # generic server-driven table (sort/filter/paginate via URL)
│   ├── charts/              # Recharts wrappers, theme-aware
│   └── <feature folders>/
├── server/
│   ├── actions/             # Server Actions, one file per domain - all return ActionResult<T>
│   ├── queries/             # read-side data access (server-only)
│   ├── api/authenticate.ts  # withApiAuth() - key verify + scope + rate limit + logging
│   └── webhooks/process.ts  # idempotent event processing
├── lib/
│   ├── auth/                # rbac, session helpers, password, totp
│   ├── payments/            # provider adapters (mock / stripe / paypal / payu) + registry
│   ├── analytics.ts         # pure MRR/ARR/churn math (unit-testable)
│   ├── api-keys.ts          # generation + SHA-256(pepper+key) hashing + verification
│   ├── rate-limit.ts        # fixed-window limiter (swap for Redis at scale)
│   ├── audit.ts / logger.ts # observability
│   └── validations/         # Zod schemas, shared client + server
├── hooks/  ·  stores/  ·  config/
└── prisma/
    ├── schema.prisma        # ~30 models
    ├── migrations/          # committed - the versioned DB template
    └── seed.ts              # Faker seeder
```

### Design principles

- **Clean architecture / SOLID** - Server Actions orchestrate, `lib/` holds pure
  logic and adapters, `server/queries` is the only place that reads the DB for
  pages. The payment layer depends on an interface, never a concrete provider.
- **Typed end to end** - DB → query → Server Action → `ActionResult<T>` → RHF field
  errors. No `any` in `src/`.
- **Money is integer cents + currency**, always. Floats only at the display edge.
- **URL as state** - every table's sort / page / filters / search live in the query
  string, so views are shareable and the RSC re-fetches on navigation.
- **Security** - hashed API keys (raw shown once), signed-webhook verification per
  provider, RBAC enforced at the edge *and* re-asserted server-side, audit log on
  every mutation, periodic JWT re-validation against the DB.

## Payment provider abstraction

```ts
interface PaymentProviderAdapter {
  isConfigured(): boolean;
  createCheckoutSession(input): Promise<CheckoutSession>;
  createSubscription(input): Promise<ProviderSubscription>;
  cancelSubscription(id, atPeriodEnd): Promise<void>;
  refund(input): Promise<ProviderRefund>;
  verifyWebhook(rawBody, headers): Promise<WebhookVerification>;
  normalizeEvent(payload): NormalizedWebhookEvent;
}
```

`getPaymentProvider(id)` returns the requested adapter, or transparently falls back
to `mock` when its credentials are absent - so checkout always works locally. Every
provider webhook is mapped onto one `NormalizedWebhookEvent` union and processed by
a single idempotent handler.

## Notes & trade-offs

- `prisma` CLI is pinned to the stable **7.10.0** because npm's `latest` dist-tag
  currently points at an `8.0.0-rc`. Remaining `npm audit` advisories are all in
  dev-only transitive dependencies bundled by the Prisma CLI (`mysql2`, unused).
- The rate limiter is in-process. For horizontal scale, swap `lib/rate-limit.ts`
  for Redis `INCR` + `PEXPIRE` - the call sites don't change.
- Sessions are stateless JWT by default; the `Session` table + "active sessions"
  UI are wired for a database-session strategy if you switch `auth.config.ts`.
